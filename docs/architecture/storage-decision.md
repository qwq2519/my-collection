# 存储技术栈决策

## 目的

记录本项目选择的存储方案、决策理由、优劣分析，供后续开发参考。

## 读者

参与本项目开发的人。

## 结论

采用 **BuntDB（主存储）+ Bleve（搜索索引）** 的组合方案。

```text
┌──────────────────────────────────────────┐
│            Go 应用 (Wails v3)            │
├──────────────────────────────────────────┤
│                                          │
│  BuntDB（主存储）      Bleve（搜索索引）  │
│  - 收藏/笔记/图片      - 标签倒排索引     │
│  - 结构化 KV 数据      - 笔记全文索引     │
│  - 内存常驻            - 模糊/组合搜索    │
│  - 自动持久化到单文件   - 中文分词         │
│                                          │
│     data.db                search.bleve/  │
└──────────────────────────────────────────┘
```

| 组件 | 包 | 定位 |
|------|----|------|
| BuntDB | `github.com/tidwall/buntdb` | 主存储，内存 KV 数据库，自动持久化 |
| Bleve v2 | `github.com/blevesearch/bleve/v2` | 全文搜索引擎，倒排索引 |

两者均为纯 Go 实现，无 CGO 依赖。

## 需求约束

| 需求 | 说明 |
|------|------|
| 高性能读 | 收藏查询、标签检索需要毫秒级响应 |
| 减少磁盘 IO | 避免频繁读写磁盘，尽量内存操作 |
| 标签前缀匹配 | `前端::React` 查询时能匹配所有 `前端::*` |
| 灵活搜索 | 图片标签细粒度，接近全文检索 |
| 笔记内容搜索 | 支持对 note 正文全文搜索 |
| 部署简单 | 桌面应用，不依赖外部服务 |

## 备选方案对比

### 候选方案

| 方案 | 类型 | 特点 |
|------|------|------|
| SQLite + FTS5 | 嵌入式关系数据库 | 生态成熟、SQL 查询、FTS5 全文搜索 |
| BuntDB + Bleve | 内存 KV + 搜索引擎 | 纯 Go、内存快查、倒排索引 |
| Badger + Bleve | 磁盘 KV + 搜索引擎 | 纯 Go、大数据量、LSM-tree |
| go-memdb + JSON 刷盘 | 内存数据库 + 手动持久化 | 极快、多索引、需自己处理刷盘 |

### 为什么不选 SQLite

- Go 调用 SQLite 需要 CGO（`mattn/go-sqlite3` 依赖 C 编译器）或用纯 Go 翻译版（`modernc.org/sqlite`，性能降 20-30%）
- Wails v3 本身在某些平台可以不依赖 CGO，引入 SQLite 会增加编译复杂度
- SQL 的表达力对本项目超配——查询模式简单且固定
- 磁盘 IO 比内存方案多（即使有 WAL）

### 为什么不选 Badger

- 本项目数据量预计在万级以下，全内存方案（BuntDB）性能更优
- Badger 的 LSM-tree 有写放大，不如 BuntDB 的 AOF 简单
- 如果未来数据量增长，可从 BuntDB 平滑切换到 Badger（API 模式相似）

### 为什么选 BuntDB + Bleve

- BuntDB：数据常驻内存，查询零磁盘 IO，符合"高性能、少磁盘读写"目标
- Bleve：专业全文搜索引擎，解决图片标签灵活搜索和笔记内容检索
- 两者都是纯 Go，无 CGO，编译和交叉编译简单
- 嵌入式设计，不需要安装和维护外部服务

## KV/JSON vs 关系型：开发差异

本项目采用 KV + JSON 存储而非关系型数据库，以下是需要注意的开发差异：

### 获得的优势

| 方面 | 说明 |
|------|------|
| 无需 migration | 加字段直接写入，不用 ALTER TABLE |
| 半结构化友好 | 不同图片可以有不同元数据，不用留 NULL 列 |
| 性能可预测 | 无 SQL 解析开销，内存直读 |
| 部署简单 | 一个文件就是整个数据库 |
| 和 Go struct 对应 | JSON ↔ struct 直接序列化，不需要 ORM |

### 需要承担的代价

| 方面 | 说明 | 应对 |
|------|------|------|
| 多条件查询要自己写 | 没有 SQL 的 WHERE/ORDER BY | 提前设计好索引，复杂查询走 Bleve |
| 关联查询是手动的 | 没有 JOIN | 用 key 前缀设计模拟层级关系 |
| 数据完整性靠代码 | 没有外键约束 | 在 Store 层封装校验逻辑 |
| 无标准查询语言 | 换引擎需重写查询 | 抽象 Repository 接口隔离存储细节 |
| 调试不如 SQL 直观 | 看数据需要写代码或导出 | 开发模式下提供数据导出/查看功能 |

### 为什么对本项目可接受

- 实体类型少（3 种：收藏、笔记、图片），关联关系简单
- 查询模式有限且可预知：按 tag 查找、全文搜、按 site 分组
- 标签用 JSON 数组比关联表更自然
- 全文搜索交给 Bleve，比 SQL LIKE 强得多
- 数据量不大，冗余存储无负担

## 职责分工

| 操作 | 走哪个组件 |
|------|-----------|
| 增删改收藏/笔记/图片 | BuntDB（写入后同步更新 Bleve） |
| 按 ID 精确查询 | BuntDB |
| 按标签精确匹配/前缀匹配 | BuntDB 自定义索引 |
| 标签模糊搜索、多标签组合 | Bleve |
| 笔记内容全文搜索 | Bleve |
| 按站点列出所有收藏 | BuntDB 前缀扫描 |

## 架构约束

1. **Store 层封装原子操作**：每次写入必须同时更新 BuntDB 和 Bleve，保证数据一致性
2. **Repository 接口隔离**：上层业务不直接依赖 BuntDB/Bleve API，方便未来替换
3. **Bleve 索引可重建**：搜索索引视为派生数据，可从 BuntDB 主数据随时重建
4. **数据格式 JSON**：Value 统一使用 JSON 字符串，便于调试和导出
