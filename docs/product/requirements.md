# 产品需求

## 目的

定义"资料收藏夹"的功能需求、交互方式和数据规模，作为开发实现的依据。

## 读者

参与本项目设计和开发的人。

## 三大功能模块

### 1. URL 收藏

#### 数据结构

- **站点（Site）**：手动收藏，代表一个网站
- **网址（Bookmark）**：具体 URL，系统按域名自动归组到对应站点下

#### 站点元数据

- title（显示名称，如"GitHub"）
- domain（完整域名，含子域名，用于自动归组）
- icon（站点图标）
- description（站点描述）

#### Bookmark 元数据

- icon（页面图标）
- title（标题）
- description（描述）
- tags（标签列表，独立于站点）

#### 域名匹配规则

按**完整域名（含子域名）**匹配。`github.com`、`gist.github.com`、`docs.github.com` 视为不同站点。

#### 行为

- 用户先收藏一个站点
- 后续添加的 URL 由系统按域名自动归组到对应站点
- **添加 URL 时，若域名无对应站点则进入临时队列**（见下方"待归组队列"）
- 每条 URL 独立打 tag，不继承站点标签
- 检索支持：title、域名、tag

#### 待归组队列

- 添加 URL 时若域名无对应站点，URL 自动进入"待归组"队列
- 队列中的 URL 保留完整元数据（title、description、tags 等），但不出现在站点分组视图中
- 用户可在队列中查看这些 URL，选择：创建对应站点（URL 自动归入）或删除
- 队列入口在 URL 模块顶部，有未处理条目时显示角标提示

#### 删除
- 不支持删除整个站点：删除站点时必须先手动删除该站点下面所有url
- 支持删除单条 URL
- 删除操作需二次确认

#### URL 存活检测

- 提供手动触发开关，点击后批量检测已收藏 URL 的存活状态
- 标记失效链接（404、超时、域名无法解析等）
- 不做自动定时检测

#### 数据规模

- URL：万级上限
- Tag：千级上限

---

### 2. 笔记

#### 格式

Markdown 格式的短笔记，结构为 **title（必填）+ body**。

#### 特点

- 轻量，不做复杂编辑器
- **不支持 tag**（暂时）
- 数据量少
- 与 URL 收藏和图片完全独立，三者 tag 体系互不关联

#### 笔记中的图片

- 笔记内容（Markdown body）中可以插入图片
- 图片来源必须是 persist 目录下已有的图片，或者复制粘贴时自动保存到 persist 目录
- 不支持引用外部 URL 图片或任意本地路径图片

---

### 3. 图片管理

#### 管理方式

- **用户手动指定**要管理的图片文件夹（支持多个）
- 每个文件夹可包含多个子文件夹，组织粒度为"一个文件夹"
- 多个文件夹之间**不能存在父子嵌套关系**（如不能同时添加 `D:\Photos` 和 `D:\Photos\2026`）
- 添加后由后台**异步扫描处理**，不阻塞 UI
- **不在用户图片文件夹中写入任何文件**，避免污染用户目录

#### 支持格式

常用图片格式：JPG/JPEG、PNG、GIF、WebP、BMP。

#### 文件变化检测

- **触发时机**：应用启动时 + 用户手动触发扫描
- **不做实时监听**（不使用 fsnotify）
- 基于 Merkle Tree + 目录 mtime 剪枝实现快速增量检测

#### 文件删除处理

用户在文件系统中删除图片后，下次扫描时自动从元数据和搜索索引中移除。

#### 数据规模

- 图片：万级（不确定，可能更多）

> 存储架构、Merkle Tree 算法、元数据文件格式等实现细节详见 [图片存储架构](../architecture/image-storage.md)。

## 搜索能力

| 模块 | 可搜索字段 | 最重要 |
|------|-----------|--------|
| URL | 域名、title、description、tag | tag |
| 笔记 | title、内容全文 | 全文 |
| 图片 | 文件名、tag | tag |

Tag 是 URL 和图片搜索的第一优先级。

### 列表排序

默认排序逻辑：**最近使用时间 > 创建时间**（最近操作过的排在前面）。

## 标签系统

### 基本规则

- 扁平结构，无真正的父子层级
- 用 `::` 模拟层级：如 `前端::React::hooks`
- 搜索 `前端` 时匹配所有 `前端::*`（前缀匹配）
- **URL 和图片各自独立的 tag 体系**，笔记暂不支持 tag
- 图片标签更灵活，粒度细，接近自由文本描述
- 总量千级上限

### 标签生命周期

- **无独立的"新建标签"功能**：用户在编辑/新建 URL 或图片时手动输入 tag，若系统中不存在则自动创建
- 输入时提供**自动补全**（基于已有标签）

### 标签管理

提供独立的标签管理页面：

- URL 标签和图片标签**分开管理**
- 支持操作：重命名、合并、删除
- 删除标签时，自动从所有关联实体上移除该标签
- 重命名时自动更新所有关联实体

## 数据持久化与备份

### persist 目录

项目维护一个 `persist/` 文件夹，**所有持久化数据集中存放**，是唯一需要备份的目录：

```text
persist/
├── main.db              ← BuntDB 主数据文件（URL、笔记、文件夹注册表）
├── search.bleve/        ← Bleve 搜索索引（可从源数据重建）
└── folders/             ← 图片文件夹数据（每文件夹独立存储）
    └── {folder_id}/
        ├── images.json  ← 图片元数据（标签、缩略图路径等）
        ├── tree.json    ← Merkle Tree 快照
        └── thumbnails/  ← 缩略图文件
```

### 备份方式

直接拷贝整个 `persist/` 文件夹即可完成完整备份和恢复。

- `main.db` 包含 URL、笔记等业务数据和文件夹注册表，是备份的核心
- `folders/` 包含图片元数据和标签，也是核心备份内容
- `search.bleve/` 可从 `main.db` + `folders/*/images.json` 重建，非必须备份但能加速恢复
- `folders/*/thumbnails/` 可通过重新扫描用户文件夹重建，非必须备份

### 数据流

```text
用户图片文件夹（只读扫描）
        │
        │ 应用启动 / 手动扫描
        ▼
persist/folders/{id}/images.json（写入图片元数据 + 标签）
persist/folders/{id}/tree.json（更新哈希树快照）
persist/folders/{id}/thumbnails/（生成缩略图）
persist/search.bleve/（同步更新索引）
        │
        │ 运行时查询
        ▼
内存（images.json 全量加载 + BuntDB 常驻 + Bleve 查询）
```

## 部署与扩展

- **纯本地单机**桌面应用
- 后续可选：开放 HTTP 接口，支持从手机浏览器 share URL 到本机、脚本自动添加等场景
- 始终为单服务器部署，不考虑多设备同步

---

## 应用设置

- 数据目录：默认为项目内的 `persist/` 路径
- 图片文件夹列表管理入口（添加/移除监管文件夹）
- 主题与外观偏好：后续前端设计时再考虑

---

## 暂不考虑

- 浏览器书签导入/导出
- 全局快捷键唤起（后续再做）
- 多设备同步
- 批量操作（批量打 tag、批量删除）
- 笔记 tag 功能
